## Question

在已确定的 Flutter macOS 应用与 Codex 首个客户端基础上，如何打包和交付？用户希望有本地引擎管理，并考虑关联 LM Studio 的默认引擎、由本应用下载官方 llama.cpp 主线或必要的其他引擎。依据证据确定首版引擎范围，区分应用管理的进程、LM Studio 管理的进程与外部既有服务；关闭窗口、退出应用、引擎崩溃或 MCP 客户端断开时，哪些服务应该继续运行？

明确连接方式、默认本机边界、端口与进程归属、模型就绪判断，以及容器开发规则中的 Mac 构建和桌面运行范围。结果应是可执行的生命周期决定，不是实现任务清单。

## Answer

### 用户确定的首版方案

- **引擎优先级**：优先 LM Studio；某个资产无法通过其实际 decision 能力验证时，再补充经验证的兼容引擎，例如对应版本官方 llama.cpp 或该资产必要的专用引擎。首版不要求用户先放弃既有 LM Studio 工作流。
- **窗口与退出**：关闭窗口后，应用、常驻模型与 MCP 继续运行；通过菜单或 Cmd+Q 明确退出时停止本应用管理的实例和 MCP。首版不建立一个在应用明确退出后继续运行的独立后台服务。
- **MCP**：采用本机 Streamable HTTP，默认仅监听 `127.0.0.1`。一个委员会入口供 Codex 与其他兼容客户端连接；客户端连接不会重复启动另一套模型。
- **Mac 范围例外**：允许 Mac 上准备 Flutter SDK 与构建必需依赖、编译 `.app`、进行桌面与原生引擎联调，并运行应用内的本机 MCP 服务。通用 Dart/widget 测试仍在容器。这个明确选择补充原 AGENTS.md 的容器规则，不授权无关依赖或系统变更。
- **首版交付**：本机直接运行的标准 Flutter macOS `.app`，先不启用 App Sandbox；正式公开分发签名、公证与 App Store 设计不属于当前交付范围。
- **工具链位置**：用户随后指定 Flutter 放在 `~/flutter`、Dart 放在 `~/dart`，并确认可在这两个空位置新建目录。项目启动脚本使用这些 SDK 路径。

### 实施边界

- LM Studio 通过公开 CLI/SDK/REST 与 runtime 管理入口关联，记录实际版本、资产与实例标识。不能直接调用其内部捆绑 binary 并把它当作公开独立引擎；不能从“支持 GGUF”或“使用 llama.cpp”推导出 decision 支持。
- 能力验收针对具体模型与引擎组合：资产完整、head 与模板匹配、typed 请求和实际概率响应符合对应接口，才能作为可用席位。不支持时明确显示原因并提供兼容引擎路径，不把普通聊天生成结果伪装为决策概率。
- **受管实例**由 JevManager 创建并负责生命周期。独立引擎用本应用持有的进程收口；由本应用经 LM Studio 公共接口创建的实例以准确实例标识卸载。**接入实例**是用户原本已有的实例，仅连接使用，明确退出不卸载它，也不结束 LM Studio 应用或服务本身。
- Flutter 应用统一管理配置、并发调度、综合结果与 MCP 入口。引擎就绪状态单独展示；MCP 工具发现不需要等全部模型冷加载完成。客户端断开不自动卸载常驻实例。
- 正常退出先停止接收新请求，再收口进行中的咨询与受管实例，最后退出应用。超时及部分失败的结果规则交给委员会工单确定；不能因一个席位失败就把其余意见隐藏，或把失败席位显示为就绪。
- MCP 协议与 SDK 采用实际 Codex 接入可验证的固定版本，遵守对应传输和本地访问边界；模型推理 API 与 MCP 端点分开。首版不额外实现 stdio 桥接。
- 本机 `.app` 仍需真实文件权限、窗口重新打开、原生引擎加载与退出验收；不启用 App Sandbox 不等于跳过实际验证，也不自动授权公开发布或使用签名凭据。

本工单确定的是运行与实施范围；当前尚未安装 SDK、编译应用、加载模型、启动 MCP 或修改 Codex 设置。

### 验收

- 用户既有 LM Studio 模型库及服务可被正确关联；支持与不支持 decision 的具体组合有真实结果。
- 同一委员会的多模型实例可同时保持就绪，多个客户端共用它们，咨询触发并发调用。
- 关闭最后窗口后，原 MCP 连接及后续调用仍有效；用户可以重新打开管理窗口。
- 明确退出后 MCP 与受管实例结束，LM Studio 本身及接入实例保持原有状态；没有本应用遗留的独立引擎进程。
- 容器内共享测试与 Mac 上编译、桌面/引擎/MCP 联调分别记录，不互相替代。
